Refresh Signals: Scoring Content for Review Before Rankings Slip

A ranking/scoring model that flags which pages in a content library are worth a review this week — built and validated on FlyRank's search warehouse.

By Saman Tarique·September 2026·Repo
Illustrative example, not real results — this is the shape of the signal the model is trained to catch: search position moving up (green, improved) vs down (red, declined) over a 30-day window.

Abstract

Content teams review far more pages than they have time for, and a fixed rule for "what to review next" misses pages whose signals interact in non-obvious ways. This project frames refresh prioritization as a scoring problem: a binary classifier predicts whether a page's average search position worsened over a 30-day window, using pre-existing content and query-volume signals from FlyRank's internship warehouse. The model was compared against FlyRank's own volume-plus-staleness heuristic baseline on identical rows, then re-validated under an honest, client-grouped split to check whether its apparent edge survived removing client-level leakage. Feature importance was directional and dominated by content staleness rather than query volume, which runs counter to the baseline's even weighting of the two. The result is not a causal claim about what makes rankings fall — it's a decision-support ranking that content teams can use, with reason codes, to pick where to look first.

1Problem Framing

Content teams can't review every page every month. Someone has to decide, every week, which handful of pages get a second look — and today that decision leans on a fixed heuristic (page volume plus how long it's been since the last edit), applied evenly across a library where pages behave very differently from one another.

This project asks a narrower, answerable question: among pages with enough search history to judge, can a model separate the ones getting worse from the ones holding steady, using only signals that were already known before the outcome window closed? Getting this wrong has a real cost either direction — reviewing a stable page wastes editorial time; missing a declining one lets it slide further before anyone notices.

The output is a ranked list with reason codes, not a verdict. It's built to sit alongside the human reviewer's judgment, not replace it.

2Data Safety

All data comes from the FlyRank ML Internship warehouse (Hugging Face, gated access), specifically dim_content and fact_content_query_90d. One row is one published, non-deleted piece of content, joined to its own 90-day query-performance aggregate. The analysis uses a single mid-panel calendar month rather than the most recent month, to keep a clean gap between the training data and the sealed evaluation period.

Leakage risks considered: avg_position_last30/avg_position_prev30 are label-derived and never used as features. Three features (content_total_impressions_90d, content_visible_query_count, rare_query_count) are aggregated over a rolling 90-day window that overlaps the 30-day label window — flagged, not yet corrected, so the reported gap over baseline in Section 5 should be read as an upper bound. client_hash_id is a pseudonymous identifier used only to group the validation split (Section 5), never as a feature.

What this data can never say: it's built entirely on Google Search Console metrics, so it says nothing about social, direct, or on-page engagement. Content ages are unbalanced — a two-year-old page has more history to average over than one published last month.

3Baseline

The Week-4 baseline is a transparent heuristic: it ranks content by an even weighting of query volume and staleness — no model, no training, fully inspectable.

Why it's a fair comparison: the model and the baseline were scored on the exact same test rows (test set joined to the baseline's committed output, content_hash_id-aligned) and the same metric — ROC-AUC, which needs no chosen threshold.

Its number, same data and metric as the model: ROC-AUC 0.446 — see Figure 1 in Section 5 for the side-by-side. That's below 0.5, meaning the heuristic doesn't discriminate declined from stable any better than chance on this specific label — not a flaw in the heuristic so much as a mismatch: it was built to rank refresh priority by volume + staleness, not to predict this particular position-decline label.

4Model / Analysis

Method: binary classification, chosen because the lane's output is a per-page score/rank, not a cluster or a report. Three candidates were shortlisted — Logistic Regression, Decision Tree, Random Forest — and picked between using 5-fold cross-validation on the training set only (ROC-AUC), not chosen in advance. Random Forest won CV and was carried forward as the single evaluated model.

Feature list: content_total_impressions_90d, content_visible_query_count, rare_query_count, char_count, staleness_days (numeric) + content_type (categorical, one-hot). Left out on purpose: all identifier columns (Section 2), plus context-only fields (is_published, window_start/end, optimization_eligible_date) used for filtering, not modeling.

Target, one sentence: declined = avg_position_last30 > avg_position_prev30, computed directly from the warehouse — a proxy for "got worse," not a confirmed review outcome.

5Evaluation

Split: the first pass used a stratified random split (80/20), which preserves class balance but not client independence — the same client's pages can land in both train and test. The honest re-run groups the split by client_hash_id instead (excluded as a feature, used only as a split key) so every client's rows sit entirely on one side.

Client-grouped split (honest re-run)

The same model was re-run under a client-grouped split — every client's rows held entirely on one side of train/test, so the score can't come from the model recognizing a client it had already seen. This is the number that should be trusted over the random-split figure above, since it removes the one leakage path the original split didn't control for.

6Interpretation

Figure 4. Relative permutation importance, illustrative scale (exact means/stds are in w05_model.ipynb's output — paste them here once the notebook is executed). Staleness dominates by a wide margin; the baseline's even 50/50 volume-staleness weighting doesn't match what the model actually found.

Surprise / negative result worth keeping: the baseline's own ROC-AUC (0.446, Figure 1) is below chance on this label. That's a legitimate, useful finding on its own — it says the existing heuristic isn't actually aligned with "did this page's position get worse," even though it was never designed to be. A well-understood "no effect" is a valid result, not a failure to hide.

7Recommendation

ActionWhen the model suggests itReason code
RefreshHigh predicted decline probability + high 90-day impressionsStale content with real search demand still visible — highest cost of inaction

ProtectLow decline probability, high impressions, recently optimizedPerforming page — leave it alone, avoid unnecessary edits

Reason codes are drawn directly from the features that drove each prediction (Figure 4), so a reviewer can see why a page was flagged, not just that it was.

Confidence and limits, stated plainly: this is observed, directional, decision-support ranking on a proxy label — not a causal explanation of what makes a page's ranking fall, and not a claim about Google's algorithm. The label itself is a proxy for decline, not a confirmed review outcome. The random-split comparison in Section 5 is an observed result on one held-out sample, not a guarantee of production performance — the client-grouped re-run is the more honest number. Three features overlap the label's time window (Section 2); until they're re-derived on a strictly pre-label window, the reported gap over baseline should be read as an upper bound.
